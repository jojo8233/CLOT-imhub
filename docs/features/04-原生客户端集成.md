## 实现位置

**桌面端宿主** — `packages/desktop/src/renderer/components/NativeClient.tsx`
- `WEB_CLIENT.telegram = 'http://localhost:1234/'`(开发期指向 Vite)
- 每账号 `<webview partition="persist:native-<accountId>">`,**建过就不卸载**,
  只用 display 切换(重载要重连、重拉会话、丢滚动位置)
- `dom-ready` 后向服务端申请五分钟 control grant，由主进程验证账号 owner、撤销版本与
  Telegram self user id；guest 只看到 typed bridge，不看到 grant 或用户 JWT
- webview 支持性检测 + 20 秒加载超时提示；外壳只记录脱敏后的 warning/error 信号，
  不转发 guest 文本或 sourceId（历史 token 仍在页面内，原样转发会泄密）
- 主进程 `will-attach-webview` 二次校验 origin/partition 并强制受控 preload；
  `native-bridge.ts` 用 requestId + contextRevision 防旧会话误发，v2 另用 attemptId
  标识一次逻辑发送；翻译 detect/batch 也只经该 preload 的窄 IPC 代理
- `NativeConversationWorkspace.tsx` — 单一会话布局：原生客户端 + 固定翻译
  输入坞 + 可拖拽客户档案
- `TranslationDock.tsx` — M2 状态机；只有 bridge ready、有效当前会话和内部 UUID
  都成立时才启用

**fork 仓库** — `../telegram-tt`(独立 git 仓库,上游自带 CLAUDE.md 要遵守)

新增文件(冲突面为零):

## 关键设计取舍

- **fork 源码而不是扒 `web.telegram.org` 的 DOM**:官方页面混淆过,选择器
  一改版就失效,而且失效时不报错、只是悄悄不翻译。
- **补丁最小化**:所有 im-hub 调用收在两个新增文件里,不得不改上游时逐处
  注释——为的是跟上游 rebase 时冲突可控。
- **webview 里的内容当不可信**：新桥接走受控 preload，只暴露 typed emit/onCommand；
  页面自报 accountId 不参与授权，外壳和服务端按 webview/账号 owner 重新绑定。
- M3-2 已把气泡翻译和语言检测改成宿主代理，并删除 12 小时 JWT 注入。guest 的全局变量
  和 im-hub 网络请求不再包含用户 JWT；主进程只在 grant 与 self id 都匹配后开放能力。

## 已知限制

- 通用宿主、当前会话和输入坞协议已经完成，但 telegram-tt 尚未发出 M2 事件；
  因此真实 Telegram 运行态仍显示等待桥接，不能当成 M3 闭环完成。
- M3-2 已完成服务端签发、主进程验证的短时 account-control grant，并绑定 guest 登录的
  Telegram self id。后续平台若接入同一协议，仍必须各自定义稳定 external id 来源。
- `composer.send` 超时表示“结果未知”，不能安全地让用户直接重试。Bridge v2 host 已提供
  稳定 `attemptId`，但 M3 guest outbox 尚未消费并持久化该值；接线后必须按同一发送尝试
  做幂等，或先核对平台会话再允许重发。
- Telegram 退出或删除 im-hub 账号会清除对应 `persist:native-<accountId>` storage/cache、
  bridge 会话和待处理能力；平台侧设备管理仍按删除接口的人工提示处理。
- 本文只描述当前 Telegram 原生实现。Signal 与 WhatsApp 分别在 M5、M6 接入，
  它们不能简单复用 Telegram webview 方案，必须沿用同一桥接协议但使用合适宿主。
- **GPL-3.0 义务**:分发补丁版需向使用者提供对应源码;Telegram 品牌/图标
  另有商标约束。上线前要过一次法务。
- 非官方客户端有平台 ToS 风险(pivot spec 已接受的代价)。
- 开发期依赖同级仓库 + Vite dev server,打包分发未完成(见 06)。
