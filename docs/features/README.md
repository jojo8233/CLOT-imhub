# 功能文档索引

按模块整理当前实现与产品目标的功能对照。**需求基准**是
`docs/superpowers/specs/2026-08-24-im-hub-design.md`(原始设计文档,下称「设计 §n」),
以及 `docs/superpowers/specs/2026-08-26-m0-product-scope.md`（当前产品范围），
本目录回答一个问题:**设计文档承诺的每一条,现在做到哪了、代码在哪。**

> 平台范围：Telegram、Signal、WhatsApp 保留，Zoom 延后。状态必须区分“平台保留”
> 和“功能已完成”，不能把后续计划写成当前能力。

## 先读这个:两条路线并存

同一个产品目标有两套实现,**都还活着**,读代码前必须分清:

| | 路线 A:自建界面 + 适配器 | 路线 B:套壳补丁版原生客户端(主攻) |
|---|---|---|
| 消息来源 | TDLib 与 signal-cli（`packages/server/src/adapters/`） | 当前只有 telegram-tt fork（`../telegram-tt`，独立仓库） |
| 界面 | im-hub 自绘「会话工作台」（现存过渡实现） | 平台原生界面；目标是统一“会话”入口的中间区域 |
| 能力 | Telegram 只完整处理纯文本；Signal 也受 signal-cli 能力上限约束 | Telegram 群组、图片、语音、贴纸、回复引用原生可用 |
| 数据 | 消息落 im-hub 库，可接档案/告警 | **消息不回报服务端**——这是当前最大缺口 |

每个模块文档里的功能都标注了所属路线。

## 文档格式约定

每个模块文件固定五段:**需求出处 → 实现状态 → 实现位置 → 关键设计取舍 → 已知限制**。
实现位置分三栏标注:`服务端`(im-hub packages/server)、`fork`(../telegram-tt)、
`桌面端`(im-hub packages/desktop)。
