- 设计 §10 智能输入区:「发送前展示译文预览,员工确认后发出」
- P1a 计划 `2026-08-24-p1a-translate-preview.md`:悬停显示原文与回译并排、
  按钮和回车都要、译文可编辑、目标语言自动跟随客户语言且可按会话锁定

## 关键设计取舍

- **与原生输入框并存而不是取代**:原生框继续管附件、语音、表情、回复引用;
  校对区只管「中文 → 外文」这一条路径。发送以**原生输入框的值**为准——
  员工可能在那里做最后修改。
- **发送走原生 `handleSend()` 而不是自己调 sendMessage**:限流、字数限制、
  回复引用、定时、静默发送这些行为全部免费保留。
- **回译只是气味测试**(P1a 计划原话):回译一致不能证明翻译正确,只能
  提示明显跑偏。防抖 600ms,失败显示「回译不可用」不阻塞发送。
- **语言自动识别设 12 字符下限**:短文本检测极不可靠——实测 "Sticker"
  被判成瑞典语。低于下限、检测出不支持语种或 zh 时一律不采用。
- **draft bridge 用模块级单例而不是 React context**:加 context 要改
  MiddleColumn 的组件结构,与「补丁最小化、方便跟上游 rebase」冲突。
- **发送后 50ms 再聚焦中文框**:等原生发送流程把 DOM 结算完;同时显式清
  `isHovering`——回车发送时鼠标常悬在已卸载的预览框上,`mouseleave`
  永远不会来。

## 已知限制

- 两套实现(工作台版 / fork 版)的样式与逻辑是**复刻关系不是复用关系**:
  fork 用 Teact 且构建独立,没法 import im-hub 的组件。改行为要两边同步改。
- 支持的目标语言白名单(12 种)硬编码在 fork 的 `ImHubComposer.tsx`。
- Telegram fork 内部的 `ImHubComposer` 与外壳输入坞暂处于迁移期。M2 接通外壳
  桥接时必须保证只保留一个可操作入口，不能让两个输入组件同时可发送。
