# 01 账号与多开

## 需求出处

- 设计 §1 目标一:「一个员工同时经营多个平台上的多个账号,互不串号」
- 设计 §5.1:Telegram = TDLib,一账号一 client 实例,session 按账号隔离
- P1 计划 `2026-08-25-p1-account-onboarding.md`:员工在客户端自助扫码接入,
  不碰服务器终端
- M0 产品范围：顶部使用“平台一级 + 当前平台账号二级”，不同平台账号不能混排

## 实现状态

| 功能 | 状态 | 路线 |
|---|---|---|
| Telegram 扫码登录(QR + 验证码 + 2FA 密码) | ✅ | A |
| Signal 关联设备二维码 | ✅ | A |
| 账号自助创建、重命名、删除、重新关联 | ✅ | A |
| 断线自动重连 | ✅ | A |
| Telegram 原生界面多账号隔离 | ✅ 开发态 | B |
| 平台一级 + 平台内账号二级导航 | ✅ M1 | 外壳 |
| 每个平台记住最后激活账号 | ✅ M1 | 外壳 |
| Signal / WhatsApp 原生客户端多开 | ❌ M5 / M6 | B |

## 实现位置

**服务端**
- `packages/server/src/adapters/telegram/adapter.ts` — TDLib 实例池
  (`clients: Map<accountId, Client>`),session 落 `data/tdlib/<accountId>/`
- `packages/server/src/adapters/signal/adapter.ts` — signal-cli JSON-RPC 适配器；一个
  进程管理多个已关联账号，im-hub `accounts.id` 与 Signal 号码双向映射
- 同文件 `driveAuth()` — 鉴权状态机:`WaitPhoneNumber → requestQrCodeAuthentication`,
  `WaitOtherDeviceConfirmation → 推 qr 挑战`,`WaitCode/WaitPassword → 推挑战等答案`,
  `Ready → connected + emitCredentials('tdlib-session')`
- `packages/server/src/api/routes/accounts.ts` — REST:创建(auditor 403,
  owner 强制取自 token)、`PATCH /:id` 改名、`DELETE /:id`(confirmName 必须
  逐字匹配,先 purge 再删行)、`POST /:id/relink`、`POST /:id/auth-answer`
- `packages/server/src/db/migrations/0003_backfill_credentials_ref.ts` —
  给存量已登录账号回填 `credentials_ref`,否则它们会静默失去自动重连

**桌面端**
- `packages/desktop/src/renderer/components/AddAccountDialog.tsx` — 添加账号
  弹窗:平台选择 → 二维码 → 验证码/2FA 输入
- `packages/desktop/src/renderer/navigation.ts` + `store.ts` — 平台范围、首次选择、
  平台内账号恢复、删除账号后的合法状态收敛
- `packages/desktop/src/renderer/components/AccountTabs.tsx` — 顶栏两级导航；一级
  Telegram / Signal / WhatsApp，二级只显示当前平台账号
- `packages/desktop/src/renderer/components/NativeClient.tsx` — 每账号一个
  `<webview partition="persist:native-<accountId>">`,partition 即独立浏览器,
  登录态互不可见——**多开就是这一行实现的**

## 关键设计取舍

- **刻意不用 tdl 的 `client.login()`**:它是为交互式终端设计的阻塞流程,
  拿不到中间状态。手动驱动 `authorizationState` 才能把二维码/验证码/2FA
  逐步推给客户端(WS `auth_challenge` 事件)。
- **`connect()` 建完连接就返回**,鉴权异步进行。阻塞式 connect 会让一个
  待登录账号卡住整个服务端启动。
- **2FA 密码内存直传**:`pendingAnswers` Map 用完即删;密码只活到
  `checkAuthenticationPassword` 返回,不写库、不打日志、不进错误消息。
- **自动重连看 `credentials_ref` 而不是 `status`**:员工在手机上解除设备授权
  后 status 仍是 connected;TDLib 数据目录在鉴权完成前就建好,也不能当依据。
- **创建/删除不走 scoped**:scoped 语义是「能看见」,这两个操作要求「是本人的」
  ——否则 manager 能替下属完成登录、拿走账号。见 `requireOwnedAccount`。
- **二维码过期不自己计时**:Telegram 会自动下发新码,跟着平台走。

## 已知限制

- 路线 A 的账号在「会话工作台」里只有纯文本消息(见 06 需求缺口)。
- 原生客户端目前只有 Telegram webview；Signal 与 WhatsApp 的原生多开尚未实现。
- 删除账号只清本机数据,平台侧登录态(手机上的已授权设备)要用户自己去移除。
