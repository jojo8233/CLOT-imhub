## 实现位置

**服务端**

  `fallbackOrder` 降级、`AllProvidersFailedError`、降级时记 `downgradedFrom`
- `packages/server/src/translation/cache.ts` — `cacheKey(provider, from, to, text)`
  → Redis,TTL 30 天
- `packages/server/src/translation/providers/{deepl,openai,claude}.ts`

  会话锁定 > 客户最近一条消息的 `body_lang` > `'en'`;`'und'` 跳过
- `packages/server/src/api/routes/translate.ts` —
  `POST /api/translate/batch`(1–50 条、单条 ≤4000 字)与
  `POST /api/translate/detect`
- `packages/server/src/pipeline/` — BullMQ 翻译任务(路线 A 的消息入库后走这里)

**fork(telegram-tt)**
- `src/util/imhub.ts` — `translateBatch` / `translateOne` /

## 关键设计取舍

- **batch 逐条并发而不是拼接成一大段**:拼接后译文遇换行会错位,单条失败
  会拖垮整批。逐条并发 + 顺序与入参严格对应 + 单条失败标 `failed: true`。
- **译文不带 Telegram entities(粗体/链接)**:原文的字节偏移在译文长度下
  必然不符,带上只会渲染错乱,刻意丢弃。
- **detect 是「借」翻译引擎**:翻成 en 拿附带的 `detectedLang`,译文丢掉;
  失败返回 `detectedLang: null` 而非报错——检测失败不应该打断任何流程。
- **自动翻译目标固定 `'zh'` 不跟界面语言**:上游跟界面语言走,界面设英文时
  会把英文消息「翻译成英文」。员工母语是中文,写死。
- **上游三道 Premium/配置门禁全部绕开**:`canTranslate` 默认值、
  `isCurrentUserPremium` 检查、无人写入的 `chat.detectedLanguage`——上游的
  「整聊天翻译」自己就没通,见 04 的补丁清单。

## 已知限制

- **目标语言解析有两套实现且不共享**:服务端 `target-lang.ts`(会话锁 +
  body_lang)与 fork 的 `ImHubComposer`(localStorage + detect API)各写各的,
  兜底语言、'und' 处理规则可能漂移。合并方向:fork 侧改调服务端解析。
- 翻译引擎全部失败时,路线 A 的客户端 UI 停在「翻译中…」不提示放弃
  (RUNBOOK 已知限制)。
- 路线 B 的翻译结果**不落库**——只存在 fork 的内存缓存里,重开就重翻
  (有 Redis 网关缓存兜底,成本可控,但无法离线审计)。
