# 06 需求缺口

集中记录尚未完成的产品能力，并标出已经消除的历史缺口，避免继续按过期设计开发。

## 1. Telegram 接入通用消息回传（M3 缺口）

M2 已完成平台无关协议、`POST /api/native/events`、owner 校验、归一化、编辑/删除、
最终 id alias 和 ACK/重试语义；但 telegram-tt fork 目前仍然**只调用** im-hub
翻译，尚未发出这些事件。后果：

- 路线 B 里收发的消息不进 `messages` 表
- 依赖消息正文的关键词告警(§9)在套壳路线下缺少完整数据源，完成回传前不能宣称告警闭环
- 人工客户档案不依赖消息正文，已在 M4-1 独立完成

M3 方向：fork 增加集中式 outbox 模块，把收发、编辑、删除和 id remap 事件交给
`window.imHubNativeBridge`；收到 `event.ack` 后移除，失败用同一 eventId 重试。

消息 id 基础已在 M3-1 解决：数据库去重键为
`(account_id, platform_message_id)`，所以协议要求 `platformMessageId` 在账号范围内
稳定且唯一。Telegram 的 id 只在 chat 内唯一，而且 TDLib 当前值与 telegram-tt 的
MTP 原始值编码不同；shared、TDLib adapter 与 fork utility 现已统一生成
`chatId:serverMessageId`，同步定义 reply/delete/remap，并由 `0005` 迁移旧 TDLib 数据。
真实 Telegram fixture 与 shadow 对账仍未完成，不能只凭单元/迁移测试宣称线上无重复。
在 telegram-tt 尚未发事件的当前状态不会产生双路重复；进入 shadow 回传前仍必须用
真实消息验证两端实现完全一致，不能把单元测试或现有 alias 表当作线上对账已经完成。

Bridge v2、数据库与翻译任务现已支持单调 `editVersion`；旧适配器仍以 `editedAt` 回退。
telegram-tt outbox 尚未实际提供版本序号，完成 M3-4/M3-5 前仍不能宣称快速连续编辑闭环。

### 固定翻译输入坞桥接

M2 的 `NativeComposerBridge` 与外壳状态机已经完成。当前保持禁用是因为 Telegram
fork 尚未发 `bridge.ready/context.changed`，属于 M3 平台接线，不是通用桥接缺失。

### M3 生产安全门槛

- M3-2 已删除 fork 页面内 12 小时 JWT 的 `window.__IM_HUB__` 历史注入；翻译 detect/batch
  改由宿主使用五分钟 account-control grant 代理。
- M3-2 已把 owner/auditor、账号撤销版本和平台 external id 的实时校验移到服务端/主进程
  边界；renderer 判断只用于 UX。
- M3-2 已将 `bridge.ready` 后上报的 Telegram `currentUserId` 与 DB 账号绑定，不匹配即阻断。
- `composer.send` 使用稳定 attempt id 做结果幂等；超时属于结果未知，不能盲重试。
- M3-2 已在 Telegram 退出或删除账号时清除对应 `persist:native-<accountId>`、bridge 会话
  和待处理能力。outbox 的同账号 single-flight/窗口限流和连接池压力测试仍未完成。

## 2. 客户档案库（M4-1 已验收；M4-2 已完成部分真实桌面验收）

当前产品只保留人工档案，不分析聊天正文，也不调用模型自动提取。六个字段为姓名、年龄/居住地、
职业/退休状况、家庭/婚姻状况、兴趣和其他。

现状：`customer_profiles` 表、受 RBAC 约束的 GET/PUT API、乐观锁和桌面右栏编辑均已实现并
通过真实保存验收。独立客户档案库的六字段、会话名称和账号名称服务端搜索，以及平台/账号筛选、
稳定分页和按权限查看/编辑已完成代码与自动化验证；独立档案库的导航、关键词搜索、平台/账号筛选、
详情、编辑保存及“翻译历史”移除已通过真实桌面验收。当前登录角色未知，owner 全局范围尚未验证，
不得表述为完整 RBAC 或人工验收。自动提取、提取建议、模型摘要和“重新提取”入口已从产品范围删除。

剩余缺口：需以 owner/admin 身份验证独立客户档案库的全局可见范围；团队/成员管理与管理后台仍未实现。
