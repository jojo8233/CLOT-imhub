# 06 需求缺口

设计文档承诺、当前**没有代码**或只有占位的部分。按阻塞关系排序——第一条
堵住了后面两条。

## 1. 消息回报服务端(路线 B 的结构性缺口)

pivot spec 写明「补丁客户端本身成为新的适配器」,但目前 telegram-tt fork
**只调用** im-hub(翻译),**不上报**消息。后果:

- 路线 B 里收发的消息不进 `messages` 表
- 客户档案(§8)和关键词告警(§9)的数据源为空——**这两个核心卖点在
  套壳路线下无法工作**,直到补上这条回报链路

方向:fork 里加一个上报模块(新增文件,符合补丁最小化原则),把收发消息
归一化后 POST 给服务端,复用现有 `(account_id, platform_message_id)` 去重。

## 2. 客户档案(设计 §8)— 未开工

设计要求:14 类字段(name / age_range / location / timezone / language /
occupation / family / interests / category_preference / budget_level / stage /
next_followup_at / taboo_topics / interaction / notes);**AI 与人工物理分离**
(`ai_summary` vs `manual_fields`,人工改过的永不被 AI 覆盖);触发 =
会话静默 10 分钟入队 + 每日兜底 + 手动重生成;Claude 结构化输出。

现状:`customer_profiles` 表未建;桌面端右栏
(`renderer/components/CustomerPanel.tsx`)是空壳界面。

## 3. 关键词告警(设计 §9)— 未开工

设计要求:字面量规则编译成 Aho-Corasick + 正则逐条;manager/auditor/owner
默认收,agent 申请-审批(`alert_permissions`);通道 = WS + 后台列表 +
邮件/企业微信 webhook;**必须有确认闭环**(open → acked)。

现状:`keyword_rules` / `alerts` / `alert_permissions` 表未建,零代码。

## 4. 审计日志(设计 §3、§14)— 只有信号位

`resolveScope` 给 auditor 算出 `requiresAudit: true`,但无任何消费方。
设计 §14 还要求:员工首次登录的监控知情确认也要写 `audit_logs`——这是
合规硬要求(员工通讯监控需事先书面告知),不是可选项。

## 5. 打包分发 — 开发期形态

- telegram-tt 靠同级仓库 `npm run dev`(:1234),未纳入安装包
- 补丁版客户端的 GPL 源码交付流程未建
- 服务端部署(docker-compose)未在生产验证

## 6. 路线 A 的媒体与显示名

TDLib 适配器只认 `messageText`,图片/文件/语音**静默丢弃**;
`senderDisplayName` 恒为 null;Telegram 群的 `conversationDisplayName`
也是 null(库里显示裸 id)。若路线 B 全面接管,这条按放弃处理;若工作台
还要用,这是首要补课。

## 7. 其他平台

- **Signal**：`signal-cli` 适配器、归一化和测试仍在，可完成关联设备与基础消息
  链路；但目标要求的原生多开、翻译、图片/贴纸保留和消息回传尚未完成，计划 M5。
  `docs/attic/signal-desktop-patches/` 只保存早期原型，不能视为可运行代码。
- **WhatsApp(§5.4)**：只有 `PLATFORMS` 枚举预留，计划 M6。
- **Zoom(§5.3)**：只有类型预留，明确延后到 M8，不阻塞首期交付。
