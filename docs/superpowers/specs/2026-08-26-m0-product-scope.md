# M0 产品范围与开发基线

日期：2026-08-26
状态：已确认，作为后续阶段的产品范围基线

## 1. 产品目标

im-hub 是跨境团队使用的多平台客服工作台。它不是把各平台消息重新画成一个
简化聊天工具，而是在统一的 im-hub 外壳内承载平台原生客户端，同时把消息、客户、
权限和审计数据回传到 im-hub 服务端。

首期保留三个平台：

1. Telegram
2. Signal
3. WhatsApp

Zoom 仍属于产品范围，但延后到三个首期平台完成之后，不进入当前交付承诺。

## 2. 必须保留的业务能力

- 四种角色：`owner`、`auditor`、`manager`、`agent`
- 团队管理
- 客户档案
- 关键词告警
- 审计日志
- 管理后台
- 消息回传与长期存档
- 多引擎翻译与发送前校对
- 图片、文件、语音、贴纸、表情回应和回复引用等平台原生能力

原生客户端只负责平台交互体验，不能绕过 im-hub 的权限、归档、告警和审计边界。

## 3. 界面信息架构

只保留一个“会话”功能，不再向用户同时展示“会话工作台”和“原生界面”两个入口。

统一界面由以下区域组成：

- 顶部：平台与账号导航
- 左侧：im-hub 功能中心
- 中间：当前平台、当前账号的原生客户端，以及固定在原生输入框下方的翻译输入坞
- 右侧：im-hub 客户档案与互动概览

右侧客户档案必须跟随原生客户端当前打开的会话。原生客户端需要通过受控桥接上报
当前会话标识，外壳再按账号权限查询对应客户资料。

翻译输入坞由 im-hub 外壳统一提供，不随原生消息列表滚动，也不能覆盖原生输入框。
员工在输入坞输入中文，译文写入原生输入框；员工可在原生输入框做最后修改，发送时
必须读取修改后的最终文本并调用平台原生发送。草稿按 `accountId + conversationId`
隔离，切换平台、账号或会话时禁止串稿。

## 4. 平台与账号多开

顶部采用两级导航，不能把所有平台账号混在同一排：

1. 一级为平台：Telegram、Signal、WhatsApp；Zoom 未来出现。
2. 二级只显示当前平台的账号。

每个平台单独记住最后一次激活的账号。切换平台时恢复该平台上次使用的账号。对依赖原生页面
观测平台 update 的路线，宿主恢复会话后必须预挂载当前 owner 的所有已支持账号；
之后进程或 webview 常驻，只切换显示状态，避免未点开账号丢 update，也避免反复登录、
重载和丢失滚动位置。这不放宽 owner/auditor 边界，权限收回时隐藏账号也必须立即卸载。

平台账号的登录态、缓存目录、浏览器 partition 或客户端 profile 必须物理隔离，不能
只依赖界面状态区分账号。

## 5. 平台接入路线

| 平台 | 目标路线 | 当前基线 | 计划阶段 |
|---|---|---|---|
| Telegram | 补丁版 `telegram-tt` + Electron webview | bridge/composer/outbox 与约定范围真实故障矩阵已完成；shadow 账本已接线，真实对账和切换门槛待完成 | M3 |
| Signal | 补丁版 Signal Desktop，以独立 profile 多开 | `signal-cli` 适配器与统一会话 UI 作为首检点；真实关联/收发待验，原生交付路线尚未完成 | M5（与 M6 并行） |
| WhatsApp | 官方 Web `web_shell` 仅保留原生页面；统一消息使用 Business Platform `cloud_api` | owner-only 隔离壳、登录与页面内原生收发首检已完成；Cloud API 仅预留模式，尚无授权、Webhook、翻译或中央回传 | M6（与 M5 并行） |
| Zoom | 后续单独评估 Team Chat 官方能力 | 只有平台类型预留 | M8 |

`packages/server/src/adapters/` 的现有适配器路线暂时保留。只有当对应原生客户端的
消息回传、发送确认、去重、鉴权和故障降级全部验收后，才能决定是否让旧适配器退出
主消息链路，不能提前删除。

## 6. 原生客户端桥接边界

每个平台的补丁客户端至少要提供以下受控能力：

- 上报当前账号和当前会话
- 上报入站、出站消息以及平台最终消息 id
- 上报消息编辑、删除、回复关系和媒体元数据
- 调用 im-hub 翻译网关
- 发送前读取和更新草稿，并触发原生发送
- 向固定翻译输入坞报告当前草稿、目标语言、翻译与发送状态
- 明确报告配置注入、加载、鉴权和进程异常

所有上报必须由服务端按登录用户与账号所有权重新校验，不能信任客户端传来的
`accountId`。消息继续使用 `(account_id, platform_message_id)` 去重。

## 7. 阶段与验收顺序

| 阶段 | 目标 |
|---|---|
| M0 | 仓库基线、产品范围、文档与 GitHub 工作流 |
| M1 | 统一外壳、单一会话入口、平台/账号两级导航与固定翻译输入坞布局 |
| M2 | 原生客户端宿主、消息回传和当前会话桥接 |
| M3 | Telegram 多开、翻译、媒体、回传和存档完整闭环 |
| M4 | 团队、客户档案、关键词告警、审计日志和管理后台 |
| M5 | Signal 首检点与原生多开完整闭环；与 M6 并行推进 |
| M6 | WhatsApp 官方 Web 隔离壳；另以 Business Platform Cloud API 完成统一消息闭环；与 M5 并行推进 |
| M7 | 集成测试、安装包、更新、部署和正式交付 |
| M8 | Zoom 未来接入 |

开发时每个阶段使用独立 Milestone；每项可验收工作使用 Issue；代码在
`codex/<阶段>-<主题>` 分支完成并通过 Pull Request 合并。一个提交只处理一个清晰
目的，禁止把未完成的平台实验与无关文档清理混在一起。

## 8. M0 完成标准

- GitHub `main`、M0 基线标签、M0-M8 Milestones 和路线图 Issue 可用
- Signal 适配器与测试没有因方向误判被删除
- 文档不再把 Signal 写成放弃，也不把未完成能力写成已交付
- Zoom 明确标记为未来阶段
- `.DS_Store`、会话数据、密钥和构建产物不会进入 Git
- `pnpm typecheck` 通过
- 测试只在确认隔离测试库后运行
